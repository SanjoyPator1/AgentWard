# fhir-mcp

An MCP server that exposes our HAPI FHIR server as tools an agent can call.
Targets the MCP 2026-07-28 specification, built on the official `mcp` Python
SDK v2.

Background reading, if the protocol is unfamiliar: `self-docs/04-mcp-fundamentals.md`.

All data behind this server is synthetic, generated by Synthea. Nothing it
produces is clinical advice or validated for clinical use.

## Running it

The FHIR server has to be up first:

```
docker compose up -d hapi-fhir          # from the repo root
```

Then, from this directory:

```
uv sync
uv run python -m fhir_mcp.server
```

It listens on `http://127.0.0.1:3001/mcp`.

To check it actually works end to end, with the server running:

```
uv run python scripts/smoke_test.py
```

That exercises every tool against real loaded data, including the error paths,
and prints what came back. No model involved.

For interactive poking there is also the MCP Inspector:

```
uv run mcp dev src/fhir_mcp/server.py
```

## Configuration

Everything is environment variables, read once at startup into `config.py`.
Defaults work against the local Docker substrate with no configuration at all.

| Variable | Default | Purpose |
|---|---|---|
| `FHIR_MCP_BASE_URL` | `http://localhost:8080/fhir` | The FHIR server to talk to |
| `FHIR_MCP_SERIALISATION` | `nested` | `nested`, `flattened`, or `compact` |
| `FHIR_MCP_TIMEOUT_SECONDS` | `30` | Per-request timeout against FHIR |
| `FHIR_MCP_HOST` | `127.0.0.1` | Interface to bind |
| `FHIR_MCP_PORT` | `3001` | Port to listen on |

## The tools

Level 1 only so far: thin passthrough over the FHIR REST API. The agent has to
know FHIR to use these, which is the point. They are the baseline that Level 2
(task-shaped tools) and Level 3 (code mode) get measured against in
Experiment 1.

| Tool | What it does |
|---|---|
| `get_resource_by_id` | Read one resource when you already have its type and id |
| `search_resources` | Search one resource type, one page at a time |
| `get_next_page` | Fetch the next page of a search already started |

**Read-only on purpose.** Create, update, and delete belong with F4, the prior
authorisation feature, where the permission gate and audit trail that should
sit in front of a write actually get designed. Shipping destructive tools now,
long before anything gates them, is the mistake B04 chapter 16 is about.

## Two design decisions worth knowing

**Paging uses an explicit handle.** The 2026-07-28 specification removed
protocol-level sessions, so there is no server-side notion of "the current
search". `search_resources` returns a `next_page_token` and `get_next_page`
takes it back as an ordinary argument. That token is a URL that left the
server, passed through a model, and came back, so it is validated as untrusted
input: `FhirClient._is_same_server` refuses anything that is not this FHIR
server. Without that check, `get_next_page` would be a request forgery
primitive pointed at anything on the Docker network.

**`total_matching` and `returned` are separate fields, deliberately.** The
first is how many resources matched across all pages, the second is how many
came back in this one. F1's whole task is proving a negative, and "no HbA1c
exists" can only be concluded from a real total, never from an empty page
someone forgot to page through. Searches request `_total=accurate` so the
server gives a true count rather than an estimate, and `total_matching` is
null rather than zero when a server declines to count, keeping "none" distinct
from "not counted".

## Serialisation, and Experiment 3

Every tool return passes through `serialization.py`, so comparing strategies is
a configuration change rather than an edit to every tool.

- `nested` returns the resource as FHIR gave it. The baseline.
- `compact` drops `text` (FHIR's XHTML narrative, which restates structured
  data), `meta`, and top-level extensions. Nested extensions are kept, since at
  depth they are sometimes the only place a value lives.
- `flattened` collapses nesting to dotted paths, e.g. `code.coding.0.display`.

An early measurement worth knowing before running the experiment properly: on
one real Condition, `nested` was 996 characters, `compact` 818, and
`flattened` **1076**. Flattening made it larger, because repeating a dotted
path prefix on every leaf costs more than the nesting it replaces. Whether
that trade helps or hurts accuracy is exactly what Experiment 3 measures, but
it should not be assumed to be a token saving.

## A bug this only surfaced once tested from outside the SDK

The first version of this server passed its own smoke test cleanly and still
did not work for a plain HTTP caller. `MCPServer.run(transport="streamable-http")`
does not set `stateless_http`, and it defaults to `False`. A request with no
`Mcp-Protocol-Version` header, which is what any client not built from this
exact SDK might send, fell into a legacy transport path expecting an
`Mcp-Session-Id` and got rejected with a bare `Bad Request: Missing session ID`.
The smoke test never caught it because it used the SDK's own `Client` on both
ends, which negotiates that header invisibly.

Fixed by passing `stateless_http=True` explicitly in `server.py`. `tests/test_wire_protocol.py`
now drives the actual ASGI app with plain `httpx`, not the SDK client, so this
specific regression is caught by `pytest` rather than by someone running curl
by hand later and wondering why it broke.

One correction while testing that same file: the specification's own prose
files "unknown tool name" under protocol errors, a top-level JSON-RPC `error`.
The installed SDK (2.1.1) does not do that. Calling a tool that does not exist
comes back as an ordinary result with `isError: true`, the same shape as any
other tool failure. The test asserts what was actually observed, not what the
spec's wording implied before checking.

## Two known deviations from the 2026-07-28 spec, both in the SDK

Audited on 2026-08-30 by driving a running server with plain `curl`, not by
reading the code. Nine of eleven checks passed: no handshake needed,
`server/discover` answers with `supportedVersions: ["2026-07-28"]`, a missing
`_meta` protocol version is rejected `-32602`, an `Mcp-Name` that disagrees
with the body is rejected `-32020`, DELETE gives 405, an unknown method gives
404 `-32601`, an `Mcp-Session-Id` sent by a client is ignored and never echoed,
a foreign `Origin` gives 403, and the listener binds `127.0.0.1` only.

Two did not pass. Both live in `mcp` 2.1.1's transport, not in this package,
and neither is reachable from any setting `server.py` controls.

**`GET /mcp` holds a stream open instead of answering 405.** This revision
removed the standalone GET stream, and says a server implementing only this
revision should answer GET with `405 Method Not Allowed`. Ours answers `200`
and keeps an SSE stream open until the client gives up. In the SDK,
`streamable_http.py` routes `request.method == "GET"` to `_handle_get_request`
with no stateless check in front of it, so the legacy stream is reachable
whatever `stateless_http` is set to.

**A protocol version header that disagrees with the body is accepted.** The
spec says the `Mcp-Protocol-Version` header MUST match
`_meta["io.modelcontextprotocol/protocolVersion"]` and that a mismatch MUST be
rejected with `400` and `-32020`. Sending header `2025-06-18` with body
`2026-07-28` returns `200` and a full tool list. The reply comes back
SSE-framed, which is the tell: the older header routes the request into the
legacy handler, which never runs the modern header-body validation. The
`Mcp-Name` half of that same rule is enforced correctly, so this is a gap in
one specific check rather than the validation being absent.

Neither is a security problem for a local substrate, and both are
backward-compatibility paths the SDK keeps on purpose. Not worked around here:
doing so means ASGI middleware intercepting requests before the SDK sees them,
which is machinery this project has no use for yet. Recorded so that a later
"why does GET hang" is a known answer rather than a fresh investigation, and
so the claim that this server targets the stateless spec stays honest about
where it stops.

## Development

```
uv run pytest          # tests
uv run ruff check .    # lint
uv run ruff format .   # format
```

The tests cover the serialisation strategies and the page-token origin check.
Both are pure logic, so they need neither a FHIR server nor an MCP server
running. Anything that needs the real substrate lives in `scripts/smoke_test.py`
instead, which is a script rather than a test because it needs Docker up.

## Layout

```
src/fhir_mcp/
  config.py          settings from the environment, validated at startup
  fhir_client.py     async HTTP client for FHIR; knows nothing about MCP
  serialization.py   the three strategies; the Experiment 3 seam
  tools_level1.py    the thin passthrough tools
  server.py          wiring, lifespan, entry point
scripts/
  smoke_test.py      end-to-end check against real data, no model
tests/
```

`fhir_client.py` deliberately imports nothing from MCP, so an oracle script or
a test can use it directly without standing up a server. The conversion from
`FhirError` to the SDK's `ToolError` happens at the tool boundary instead.
That conversion matters: raise `ToolError` and the model receives the message
and can correct itself, let anything else escape and the SDK treats it as a
crash and the model is told only "Error executing tool `<name>`".
